## 2. Authentication & Headers

Every payment API request requires your merchant API Key and a unique client-generated Idempotency Key:

```http
POST /api/v1/payments HTTP/1.1
Host: localhost:8000
Content-Type: application/json
Accept: application/json
X-Api-Key: tiq_live_swiftpay_test_key_001
Idempotency-Key: 9b1deb4d-3b7d-4bad-9bdd-2b0d7b3dcb6d
```

| Header | Description | Required | Example |
| :--- | :--- | :---: | :--- |
| `X-Api-Key` | Merchant secret API key starting with `tiq_live_` or `tiq_test_`. | **Yes** | `tiq_live_swiftpay_test_key_001` |
| `Idempotency-Key` | Unique UUIDv4 generated by client per payment attempt. | **Yes** | `d4e5f6a7-1234-4567-89ab-cdef01234567` |
| `X-Correlation-ID` | Distributed request trace ID. Generated automatically if omitted. | Optional | `trace-889900` |

## 3. Distributed Idempotency & Anti-Tampering Engine

To prevent double-charging customers during network retries or connection timeouts:

1. **Distributed Mutex Lock (`SET NX EX 10`)**:  
   If multiple concurrent HTTP requests arrive with the exact same `Idempotency-Key`, Redis acquires an exclusive distributed lock. The second request is paused until the first finishes.
2. **Canonical Payload Fingerprinting**:  
   TransactIQ computes a recursive SHA-256 digital digest of your request payload (ignoring volatile card CVVs).  
   - If an identical payload is replayed, TransactIQ returns `HTTP 200 OK` with header `X-Idempotent-Replay: true` returning the original transaction without charging the customer again.
   - If the request body was altered (e.g. amount or currency tampered with), the server rejects it with **`HTTP 422 Unprocessable Entity (Payload Mismatch)`**.

## 5. Webhook Signature Verification (HMAC-SHA256)

Every outbound webhook delivery includes a security header:
```http
X-TransactIQ-Signature: t=1759618800,v1=a1b2c3d4e5f6...
```
Where `t` is the timestamp and `v1` is the computed signature `HMAC_SHA256("${timestamp}.${raw_payload}", webhook_secret)`.

### Node.js / Express Verification
```javascript
const crypto = require('crypto');

function verifyWebhook(payloadString, signatureHeader, secret) {
    const parts = Object.fromEntries(signatureHeader.split(',').map(p => p.split('=')));
    const timestamp = parts.t;
    const expectedSignature = parts.v1;

    const computed = crypto
        .createHmac('sha256', secret)
        .update(`${timestamp}.${payloadString}`)
        .digest('hex');

    return crypto.timingSafeEqual(Buffer.from(computed), Buffer.from(expectedSignature));
}
```

### Python 3 Verification
```python
import hmac
import hashlib

def verify_webhook(payload_bytes: bytes, signature_header: str, secret: str) -> bool:
    pairs = dict(item.split('=') for item in signature_header.split(','))
    timestamp = pairs['t']
    expected_sig = pairs['v1']

    signed_payload = f"{timestamp}.".encode('utf-8') + payload_bytes
    computed_sig = hmac.new(secret.encode('utf-8'), signed_payload, hashlib.sha256).hexdigest()

    return hmac.compare_digest(computed_sig, expected_sig)
```

### PHP Verification
```php
function verifyWebhook(string $payload, string $signatureHeader, string $secret): bool
{
    parse_str(str_replace(',', '&', $signatureHeader), $parts);
    $timestamp = $parts['t'] ?? '';
    $expected = $parts['v1'] ?? '';

    $computed = hash_hmac('sha256', "{$timestamp}.{$payload}", $secret);

    return hash_equals($computed, $expected);
}
```

## 6. Segregation of Duties (Institutional RBAC)

When querying administrative or compliance APIs with user bearer tokens:

* **Platform Administrator (`admin@transactiq.io`)**: Full write access, merchant lifecycle management, system overrides.
* **Operations Lead (`ops@transactiq.io`)**: Transaction monitoring, manual webhook replay, settlement triggers.
* **Compliance Auditor (`auditor@transactiq.io`)**: Strictly **read-only** access to ledger integrity and chained audit trails.
* **Merchant Operator (`admin@swiftpay.com`)**: Scoped strictly to merchant tenant data.
